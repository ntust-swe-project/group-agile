# AI 使用紀錄規範(給人與 AI 共同遵守)

本規範落實 `project-common/docs/VISION.md` 第 11 節第 5、7 條與 `AI_LOG_TEMPLATE.md`。
目的:讓三個人的紀錄**欄位一致、可直接匯總統計**,作為與其他兩組比較的證據。

> 給 AI 的指示:當使用者要求記錄、或你完成一次會產生程式碼/文件的協助時,
> 依本文件**起草**一筆紀錄,但**不得自行編造**「結果、理由、工時」,這三項必須由人確認。

## 1. 檔案與責任
| 檔案 | 內容 | 誰寫 |
| --- | --- | --- |
| `README.md` | 工具揭露(工具/版本/模型/自動化) | 角色 C |
| `log-<GitHub 帳號>.md` | 個人使用紀錄 | 各人自己 |
| `stats.md` | 統計 | 角色 C 匯總 |

- 一人一檔,避免 merge 衝突。檔名用 GitHub 帳號:`log-yichieh-chen.md`、`log-anitaaa17.md`、`log-eden2289.md`。
- 從 `log-TEMPLATE.md` 複製。commit scope 用 `ai-log`。

## 2. 什麼時候要記
**要記**:AI 產出了你**採用、修改或拒絕**的程式碼、設計、需求、測試、文件。
**不用記**:只問語法/概念且沒影響產出、純拼字文法修正、當天完全沒用 AI。
原則:**當下記,不要事後補**。一個任務做完、commit 之前就記完。

## 3. 一筆紀錄 = 一件事
欄位(順序固定,與範本一致):

| 欄位 | 填法 |
| --- | --- |
| # | 該檔內流水號,從 1 起,不重複、不重排 |
| 日期 | `YYYY-MM-DD` |
| 任務 | 對應的 Issue 編號與簡述,例 `#12 危機波次` |
| 問了什麼 | 一句話,寫意圖而非貼整段 prompt |
| 結果 | 只能是 `接受` / `修正後接受` / `部分接受` / `拒絕` |
| 標記 | `API` / `INV` / `DUP`,可並列,可空白 |
| 理由 | 見第 4 節;拒絕與修正必填 |
| 工時 | 單位 h,0.25 為最小刻度 |

### 結果怎麼選
- `接受`:原樣採用。
- `修正後接受`:改過才採用。**理由要寫改了什麼**。
- `部分接受`:只拿一部分。**理由要寫拿了哪部分、丟了哪部分**。
- `拒絕`:完全不用。**理由要寫為什麼**。

### 標記怎麼選(最容易混,務必分開)
- `API`:AI 給的 Godot API 過時或不存在,對照 `docs.godotengine.org/en/4.7/` 驗證不到。這是版本雜訊。
- `INV`:AI 自己加了 VISION 沒有的需求或機制(例如「忠誠度」)。這才是要比較的現象。
  - 只算 **AI 提出**的;組員自己想到、VISION 沒有的東西不算 `INV`(那是 PO 要決定收不收的 story)。
  - 被拒絕的也要記:結果填 `拒絕`、標記照樣填 `INV`。拒絕的 `INV` 正是報告要的證據。
- `DUP`:AI 只是在重現《缺氧》等參考遊戲的設計。算 `INV` 的一種,但 VISION 第 2 節要求特別記錄。
- 判斷不出來是 `API` 還是 `INV` 時:能對到 VISION 條文就不是 `INV`;查得到 4.7 文件就不是 `API`。
- 驗證不到的 API 在理由裡加註 `unverified`。

### 工時怎麼算
實際花在這件事上的時間,**包含 review 與修正 AI 產出**,不只是等 AI 回應。估不準就取最近的 0.25h。

## 4. 理由怎麼寫
寫「為什麼」,不是「做了什麼」。好的理由要能讓沒參與的人看懂:
- 好:`多出「忠誠度」,VISION 沒有此概念,且與殖民者為合作關係衝突`
- 壞:`不太對` / `改了一下`

## 5. 不要記的內容
- 不貼 API key、token、帳號密碼、個人資料。
- 不貼整段 AI 長篇輸出;需要時只引用關鍵句或連到 commit/PR。
- 客戶訪談紀錄不寫在這裡(VISION 第 9 節第 4 點另存)。

## 6. 與 commit 的對應
- 有 AI 協助的 commit 要在 footer 揭露,格式依 `COMMIT_CONVENTION.md`:
  - 用 Claude:`Co-Authored-By: <模型> <noreply@anthropic.com>`(這個 email 只適用 Claude)。
  - 用其他 AI 工具:照 Linux kernel 寫法 `Assisted-by: <工具>:<模型>`,例 `Assisted-by: Copilot:gpt-5`。
- 這是**交叉核對用**:角色 C 可用 `git log` 找出有 `Co-Authored-By` / `Assisted-by` 但 ai-log 沒對應紀錄的 commit。
- 業界作法:Linux kernel 等開源專案用 `Assisted-by: 工具:模型` trailer 揭露 AI 協助,並明定 AI 不得自行加 `Signed-off-by`,責任由人負。我們沿用 project-common 的 `Co-Authored-By`,但同樣原則:**人對產出負責**。

## 7. 工具揭露(`README.md`)
工具、模型或自動化設定有變動時**新增一列**,不改舊列。要寫:工具名稱與版本、主要模型、啟用的自動化(CCGS hooks、agent 編排、slash command)、其他工具。
**加 hook 或更動 CCGS 設定前先告知角色 C 與 PO。**

## 8. 檢查流程
1. 每人每晚同步多報一行:`ai-log 今天記了 N 筆`。
2. PR 勾選「AI 使用已記入 ai-log」,未勾不 merge。
3. 角色 C 每天掃漏記,並檢查 `API` 與 `INV` 沒有混用。
4. 有疑問的紀錄,角色 C 在 PR/Issue 留言請當事人補,不自行改別人的紀錄。

## 9. 給 AI 的起草流程
當使用者說「記一下」或任務結束時:
1. 讀取該使用者的 `log-<帳號>.md`,取得下一個流水號。
2. 依本規範起草一列,**結果、理由、工時以 `TODO(人填)` 佔位**,除非使用者已明說。
3. 對照 VISION 與 Godot 4.7 文件,**建議**標記,並說明依據;最終由人決定。
4. 只在使用者確認後才寫入檔案。不可修改他人的 log 檔,不可更動舊列。
